## 🗃️ Esquema Actualizado de la BD MRP con RLS

> Suponemos que la base de datos se llama `mrp_db`.

### 1. Habilitar `app.current_tenant` como variable de sesión
```sql
-- Permitir que la app defina esta variable
ALTER DATABASE mrp_db SET app.current_tenant = '';
```

### 2. Tabla de ejemplo: `items` (con RLS)
```sql
CREATE TABLE items (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    code TEXT NOT NULL,
    name TEXT NOT NULL,
    type TEXT CHECK (type IN ('raw', 'semi', 'finished')),
    unit TEXT,
    metadata JSONB DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Restricción: tenant_id debe existir en auth_db.companies (validado en app)
    CONSTRAINT valid_tenant CHECK (tenant_id IS NOT NULL)
);

-- Índice
CREATE INDEX idx_items_tenant ON items(tenant_id);

-- 🔒 Activar RLS
ALTER TABLE items ENABLE ROW LEVEL SECURITY;

-- Política: solo ver/modificar filas del tenant actual
CREATE POLICY tenant_isolation_policy ON items
    USING (tenant_id = current_setting('app.current_tenant')::UUID)
    WITH CHECK (tenant_id = current_setting('app.current_tenant')::UUID);
```

### 3. Aplicar lo mismo a **todas las tablas del MRP**
Ejemplo para `bom`, `inventory`, `production_orders`, etc.:

```sql
-- Plantilla genérica (reemplazar <table_name>)
ALTER TABLE <table_name> ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_policy ON <table_name>
    USING (tenant_id = current_setting('app.current_tenant')::UUID)
    WITH CHECK (tenant_id = current_setting('app.current_tenant')::UUID);
```

> ✅ Esto garantiza que **ni siquiera un superusuario** pueda acceder a datos de otra empresa **a menos que cambie manualmente `app.current_tenant`**, lo cual solo haría en operaciones administrativas controladas.

## 🔐 Flujo de Autenticación en la Aplicación (Web/API)

```python
# Ejemplo en Python (FastAPI/Flask/Django)
def authenticate_user(token: str):
    payload = decode_jwt(token)  # Valida firma y expiración
    user_id = payload["sub"]
    company_id = payload["company"]  # UUID de la empresa seleccionada
    
    # Validar que el usuario pertenece a esa empresa (opcional, ya hecho en auth_db)
    if not user_has_access_to_company(user_id, company_id):
        raise Forbidden()
    
    # Establecer el tenant en la conexión PostgreSQL
    db.execute("SET app.current_tenant = %s", (str(company_id),))
    
    return user_id, company_id
```

> 📌 **Importante**: Cada conexión de base de datos debe ejecutar `SET app.current_tenant` **al inicio de cada request**. No reutilices conexiones sin limpiar o restablecer este valor.

## 💾 Estrategia de Backups

### 1. **Backup completo diario (recomendado)**
```bash
pg_dump -h localhost -U mrp_user -d mrp_db --format=custom --file=mrp_full_$(date +%Y%m%d).dump
```

### 2. **Backup por empresa (para cumplimiento o migración)**
Usa `pg_dump` con `--data-only` y filtro por `tenant_id`:

```bash
# Ejemplo: respaldar solo datos de la empresa 'abc123...'
TENANT_ID="abc12345-6789-0000-0000-000000000000"

pg_dump -h localhost -U mrp_user -d mrp_db \
  --data-only \
  --table=items \
  --table=bom \
  --table=inventory \
  --table=production_orders \
  --where="tenant_id = '$TENANT_ID'" \
  --format=plain \
  --file=backup_tenant_$TENANT_ID.sql
```

> ⚠️ Nota: `--where` aplica a **todas las tablas listadas**. Asegúrate de incluir todas las tablas del MRP que contengan `tenant_id`.

> ✅ Ventaja: Puedes entregar un backup limpio a un cliente o migrar una empresa a otro entorno.

## 🧪 Pruebas de Seguridad (Recomendadas)

1. **Conexión sin `app.current_tenant`** → debe devolver 0 filas.
2. **Conexión con `tenant_id` incorrecto** → debe devolver 0 filas.
3. **Intento de INSERT con `tenant_id` distinto al actual** → debe fallar (`WITH CHECK` en RLS).

Ejemplo de prueba SQL:
```sql
-- Simular conexión de app
SET app.current_tenant = 'abc12345-6789-0000-0000-000000000001';

-- Esto funciona
INSERT INTO items (tenant_id, code, name, type)
VALUES ('abc12345-6789-0000-0000-000000000001', 'ITEM-001', 'Tornillo', 'raw');

-- Esto FALLA (gracias a RLS + WITH CHECK)
INSERT INTO items (tenant_id, code, name, type)
VALUES ('otro-tenant-id...', 'ITEM-002', 'Tuerca', 'raw');
-- ERROR: new row violates row-level security policy for table "items"
```

## ⚙️ `app/nginx/default.conf`

```nginx
server {
    listen 80;
    server_name localhost;
    root /var/www/html;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass php_base:9000;  # ← ¡Nombre del servicio FPM!
        fastcgi_index index.php;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }

    # Bloquear archivos sensibles
    location ~ /\.ht {
        deny all;
    }
}
```

> ❗ **Importante**: `fastcgi_pass php_base:9000` **no funcionará** porque NGINX y PHP-FPM están en el mismo contenedor en esta configuración.

## ✅ `Dockerfile` corregido (NGINX + PHP-FPM en un contenedor)

```dockerfile
# app/Dockerfile
FROM php:8.3-fpm

# Instalar NGINX y extensiones
RUN apt-get update && apt-get install -y \
    nginx \
    libpq-dev \
    && docker-php-ext-install pdo pdo_pgsql

# Copiar configuración de NGINX
COPY nginx/default.conf /etc/nginx/sites-available/default

# Copiar código
WORKDIR /var/www/html
COPY src/ .

# Limpiar caché
RUN apt-get clean && rm -rf /var/lib/apt/lists/*

# Exponer puerto
EXPOSE 80

# Iniciar NGINX y PHP-FPM
CMD service nginx start && php-fpm
```

> ✅ Ahora NGINX y PHP-FPM corren en el mismo contenedor → `fastcgi_pass 127.0.0.1:9000;`
